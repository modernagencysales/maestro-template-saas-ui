# WP-6.2 Template Instance Wiring Integration Request

Owner: root integration controller

Trigger: mechanically wire this speculative leaf only after the controller has
accepted CP-7 and CP-8. Do not integrate it into either checkpoint candidate,
and do not create a release, tag, deployment, or provider/data write from this
request.

Source contract:

- `packages/template-core/src/templateInstance/index.ts` exports
  `TemplateInstanceSchemaProvider` and `templateInstanceSchemaProvider`;
- consumers that only inspect App Map provenance should depend on
  `Pick<TemplateInstanceSchemaProvider, "provenance" | "parseText" | "resolve">`;
- `tooling/generators/src/templateInstanceMigration.ts` exports
  `createTemplateInstanceMigration(provider)`; and
- `tooling/release/src/customerTarget/templateInstance.ts` exports
  `createReleaseTemplateInstanceConsumer(schema, migration)`.

Requested mechanical wiring:

1. Add the narrow `@maestro-template/template-core/templateInstance` package
   subpath export. Do not add the contract to a broad root barrel unless an
   existing consumer requires that barrel.
2. Export the generator migration factory and release consumer from their
   controller-owned package entrypoints.
3. Instantiate one generator migration with `templateInstanceSchemaProvider`.
   Route generator template-instance build/parse leaves through that instance;
   remove the generator-local `TemplateInstance` version authority while
   retaining its app-specific projection fields.
4. In CLI customer-create composition, instantiate the release consumer from
   that same schema provider and migration, then pass it as the optional second
   argument to `createCustomerReleaseAdapter`. Keep the CP-5 release facts and
   immutable binding checks unchanged.
5. Give Agent A's App Map adapter only the narrow `Pick` interface above. App
   Map may project provenance and the resolution packet; it must not duplicate
   version constants or become release authority.
6. Regenerate only future customer/release projections after the controller
   accepts the wiring. Never rewrite either checked-in alpha release directory.

Required integration evidence:

- focused template-core, generator template-instance, and release tests pass;
- template-core, generators, release tooling, Agent A's package, and CLI
  composition typecheck and lint;
- one source scan shows pack, CLI, template, workflow-schema, compatibility-set,
  host-range, and support constants only in the canonical template-core schema
  (tests and immutable manifests excluded);
- current, previous, older/skipped, and newer golden packets remain exact;
- both alpha manifest hashes remain
  `0b55fd0895ecbcf6743860551ed52f165b4252c17ea94ad1687163a8ce6c6b93` and
  `532c0da941bce540648b38c4fb868a35b7f37ff9d2623ff5778cd922866168f6`; and
- `git diff --check` passes.

Out of scope for this request: upgrade apply, rollback/merge engines, release
manifest mutation, tag creation, release authority changes, provider or data
migration writes, broad SemVer support, shared gate/Justfile/root-script edits,
and any integration before CP-7 plus CP-8 acceptance.
